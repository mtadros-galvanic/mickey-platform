Mickey infrastructure · declared topology review

How every VM fits together—and where Ansible begins and ends

The short version: one Proxmox host runs nine Terraform-managed Linux guests plus one manually imported Windows 7 guest. The mickey-infra VM is the shared-services and storage hub; Terraform builds machines, Ansible configures operating systems, and a separate runtime repo deploys Traefik, Consul, and observability.

01 · Mental model

Three automation layers, one deliberate manual exception

The easiest way to understand the system is by responsibility, not by filename.

Terraform: machine construction

Terraform talks to Proxmox. It clones cloud-init templates, assigns VMIDs, CPU, memory, disks, NICs, startup policy, and cloud-init network/user settings. It also writes the generated Ansible guest inventory after it knows each target IP.

Ansible: host and operating-system configuration

Ansible connects over SSH, applies the Proxmox host baseline, installs common guest packages and admin tooling, and then adds role-specific behavior such as Samba/NFS, Docker, Consul clients, Yocto tooling, project sync, or website development dependencies.

mickey-infra repo: runtime services

The platform repo prepares the infra VM; it intentionally does not own the full application runtime. The sibling runtime repo deploys Traefik, the Consul server, Grafana, Prometheus, Loki, Alloy, exporters, and infra-owned Consul registrations.

Manual exception: mickey-ise7

The preserved Windows 7/Xilinx environment is imported from a VMware VMDK chain. It is not a normal cloud-init clone, is excluded from the generated inventory, and does not receive the Linux Ansible baseline.

04 · Role deep dive

What each class of VM is actually for

Infra: the shared-services boundary

mickey-infra exists so file serving and platform services do not run directly on the hypervisor. Ansible prepares disks, mounts /srv/share and /srv/mickey-shared-fast, exposes local aliases under /mnt, configures Samba and NFS, enables Docker, and publishes the persistent-tools depot.

The separate runtime repo then launches Traefik, Consul, and observability containers. This separation lets Proxmox maintenance remain distinct from service-stack changes.

ERP: reserved application capacity

mickey-erp is a deliberately roomy Ubuntu 24 guest for ERP workloads. It gets the common baseline, CIFS/NFS mounts, and a host-level Consul client, but the platform repo does not invent or deploy an ERP application. The future application repo should own its process and Consul service definition.

Build fleet: explicit, capacity-aware workhorses

The three build guests all use large bulk disks so expensive Yocto trees do not consume the fast VM datastore. They receive build packages, SSH/repository wiring, share helpers, fetch diagnostics, and a Yocto throttling service. The architecture assumes heavy builds are scheduled intentionally rather than all consuming host capacity at once.

  • Thud preserves Ubuntu 18 and Node 16 compatibility and remains off unless needed.
  • Scarthgap is the modern Protech/Digi Embedded Yocto slot, uses Node 24, enables periodic build throttling, and puts BitBake TMPDIR on /mnt/yocto-local.
  • Brimstone shares the Ubuntu 22 baseline but intentionally syncs only brimestone and Protech.

Utility fleet: disposable specialization with a common baseline

mickey-at4, mickey-tmp, and mickey-controller all receive Ubuntu 26, the shared mounts, Node 24 tooling, admin dotfiles, Codex/Claude integration, and optional project synchronization. They intentionally do not belong to consul_client_vms.

mickey-controller is the only utility VM marked for Proxmox autostart and is the designated host for Codex and Claude fleet-update timers.

Website development: dynamic address, service-aware guest

The website VM is the only DHCP guest. Terraform forces it to start during initial provisioning, installs QEMU guest-agent vendor data, waits for the selected eth0 address, and refuses the topology if exactly one useful IPv4 cannot be resolved. Ansible installs Docker, mounts the shares, configures GitHub credentials, and clones the website repo once. Its role vars disable the normal Chrome install and enable the Lavish client from persistent tools.

Windows ISE: deliberately outside the normal model

The import flow resolves the active VMware snapshot chain, converts it locally to one qcow2, uploads it through the Proxmox API, and creates VMID 703 with legacy-compatible virtual hardware. Windows-side Xilinx/Digilent setup, RDP enablement, and cable validation remain manual. Rebuilding an existing VM is also intentionally not automated.

05 · Data and service flow

Why mickey-infra is the hub without becoming the hypervisor

mickey-share: general shared data over SMB

The system of record is /srv/share on mickey-infra. The infra VM bind-mounts that locally as /mnt/mickey-share; other Linux guests and the Proxmox host mount the Samba export at the same path. Build guests also get explicit mickey-share-mount and mickey-share-umount helpers so operators can treat it as an artifact exchange boundary.

mickey-shared-fast: fast cross-host working data

The infra VM mounts the fast device at /srv/mickey-shared-fast, exposes /mnt/mickey-shared-fast locally, and exports it over NFSv4.2 to the LAN. It carries shared Codex/Claude state, global and host-private skills, and host-specific pnpm stores. The NFS export uses root_squash and maps anonymous access to UID/GID 1000.

persistent-tools: centrally built, read-only clients

The infra VM owns /srv/persistent-tools, builds pinned shared tools such as Galvanic UI and Lavish there, and exports it read-only over NFS. Clients mount it at /mnt/persistent-tools. This gives every managed guest the same built artifacts without making each guest a separate build authority.

Consul + Traefik: decentralized application registration

The Consul server and Traefik live in Docker on mickey-infra. ERP, website, and build VMs run host-level Consul clients installed by Ansible. Application repos own the files they place under /etc/consul.d; Traefik reads the resulting Consul Catalog. Infra-owned public endpoints stay in the runtime repo. The current runtime path is plain HTTP, not TLS/ACME.

06 · Ansible mechanics

From Terraform output to repeatable role-specific configuration

Ansible is not discovering the fleet independently. It consumes one tracked host inventory and one Terraform-generated guest inventory, then composes variables and tasks from group membership.

1. Inventory

ansible/inventory/hosts.yml is small and tracked: it contains only mickey-pve at 10.25.1.207, using root SSH.

ansible/inventory/hosts.generated.yml is written by Terraform and ignored by Git. It contains all nine Linux guests, SSH metadata, role metadata, and groups such as build_vms, utility_vms, and consul_client_vms. Guest playbooks receive both inventory files; the host-only playbook receives only the static one.

2. Group membership

Terraform derives role groups from each VM’s role field. The separate boolean consul_client creates an orthogonal membership: a build VM is both build_vms and consul_client_vms. That is why the shared admin layer can say “install Consul if this host belongs to the Consul group” without duplicating the decision in every playbook.

3. Variables

group_vars/all.yml establishes the common contract: admin user, mount paths, package baseline, tool pins, Codex/Claude locations, GitHub auth settings, dotfiles, NFS options, and feature switches. Role files add packages and specialized paths. Playbook-local vars set host-specific differences such as Node 16 on Thud versus Node 24 elsewhere.

The checkout mirrors these group-variable files under both ansible/group_vars and ansible/inventory/group_vars; the inventory-adjacent copy is available when the inventories are loaded.

4. Secrets

scripts/run-ansible.sh requires both ansible-playbook and sops. It decrypts secrets/prod.sops.yaml into a temporary file, registers a cleanup trap, passes the temp path as secret_vars_file, and lets each playbook include it. Secret-bearing copy/shell operations generally use no_log: true. Missing Samba credentials cause role playbooks that need the share to fail early.

5. Base layer

bootstrap-vm-base.yml disables continuous discard on the root filesystem, enables periodic trim when supported, installs the evaluated package list, pins Chrome, GitHub CLI, Herdr, and D2, configures the bootstrap admin user and authorized keys, and normalizes the hostname and local hosts entry.

Build VMs select a raw-APT path because the legacy environment cannot always rely on a modern Python interpreter at the beginning of the run. Thud additionally bootstraps a newer standalone Python specifically for Ansible compatibility.

6. Role layer

Each playbook then adds only its role’s responsibilities: infra disk/export setup; ERP share mounts; utility project sync; website Docker and repo clone; or build packages, SSH bundles, repositories, diagnostics, throttling, and device tooling. The Proxmox host playbook is separate because it manages repositories and physical storage, including the guarded /dev/sda bulk-datastore initialization.

7. Admin tooling

configure-vm-admin-tooling.yml is the post-mount composition point. It conditionally installs the Consul client, then Codex and Claude, shared auth wiring, managed guidance, dotfiles, GitHub Packages credentials, and the persistent-tools client. Doing this after mounts exist matters because Codex/Claude state and pnpm stores deliberately point into shared storage.

8. Repeatability

The playbooks are designed to be rerun: normal Ansible modules express desired state, while raw shell blocks explicitly check current versions, mounts, files, or service state and emit changed only when appropriate. “Repeatable” does not mean risk-free: storage initialization, VM import, repository cleanup, and external downloads have stronger preconditions and explicit guards.

07 · Operator workflow

The intended order of operations and why the order matters

  1. Build the required Proxmox cloud templates. Ubuntu 24 is the default server template; separate targets create Ubuntu 18, 22, and 26 templates. Terraform validates that exactly one matching template exists for every requested template name.
  2. Prepare encrypted inputs. Non-secret topology lives in envs/prod/terraform.tfvars; the Proxmox token, SSH keys, guest password hash, Samba password, and package credentials come from the SOPS file.
  3. Initialize, plan, and apply Terraform. The apply constructs the nine Linux VMs, waits for the DHCP guest’s agent-reported address, and writes hosts.generated.yml.
  4. Configure the Proxmox host baseline. This sets no-subscription repositories, validates the exact 4 TB Seagate disk model, creates the bulk datastore only with an explicit wipe confirmation, and prepares SMB/NFS client mounts. This step is intentionally guarded because it crosses a physical-storage boundary.
  5. Attach/cut over data disks before configuring infra. The docs require the existing Samba data disk to be moved from mickey-main to mickey-infra. Fast-shared storage is also identified and mounted by the infra playbook. Disk identity must be correct before Ansible formats or exports anything.
  6. Run make ansible-infra. This establishes the shared storage and tooling foundation on which the other guests depend.
  7. Run the relevant guest role playbooks. ERP, utility, website, and each build guest have explicit Make targets. Build playbooks are intentionally omitted from the aggregate site.yml because build capacity and legacy compatibility are operated deliberately.
  8. Deploy the runtime stack from mickey-infra. Its own bootstrap/deploy scripts start the core and observability containers after the platform layer is ready.
  9. Import Windows 7 separately if needed. Dry-run chain resolution first, then perform the conversion/upload/import. Finish the Windows-only driver and Xilinx steps inside the guest.

08 · Important caveats

Things the diagrams intentionally do not smooth over

Declared state is not live state

started = true is a Terraform desire, not proof that a VM is running now. Likewise, the generated DHCP address is the last address Terraform wrote after a successful resolution. A live status answer would require a separate read-only Proxmox/guest check.

Infra disks cross automation boundaries

The current tfvars declare a 2,048 GB scsi1 disk for infra, while the architecture notes also require manual reattachment of an existing 2 TiB Samba data disk and describe separate Kingston NVMe passthrough for the fast share. The safe interpretation is that identity and cutover of these data devices remain operator-controlled, even though the desired attachment/mount shape is documented in code.

Build VMs are not an always-on cluster

Scarthgap and Brimstone are currently desired “started” after apply, but none of the three build VMs is configured to autostart with Proxmox. The docs explicitly say heavy builds should be capacity-planned and that Thud/Scarthgap are not meant to run heavy work simultaneously.

Service ownership is decentralized

Ansible installs Consul clients; it does not own every application registration. The runtime repo owns infra endpoints, while application repos own their service definitions. This avoids a central config edit for every app but means troubleshooting must consider both the host agent and the application repo.

The current edge is plain HTTP

The mickey-infra README says active deployment is HTTP-only, with no TLS, ACME, or reverse-proxy authentication. That is an explicit current constraint, not something hidden by the topology diagram.

Host-key checking is disabled

ansible.cfg sets host_key_checking = False and uses IdentitiesOnly=yes. This makes rebuilds and a private-lab workflow smoother, but it weakens SSH host-identity verification and should be understood as part of the current trust model.
